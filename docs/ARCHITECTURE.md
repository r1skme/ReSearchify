# Architecture, version 2

## Runtime boundaries

`researchify_core` contains six implementation modules. `engine` owns the indexing/search/snapshot lifecycle; `disk` owns paged dictionaries, bounded external sorting and compressed postings; `query` owns lexing, parsing, UTF-8 tokenization, Thompson NFA and conservative regex filters; `json` owns strict JSON parsing/writing; `api` owns one command registry, schemas, CLI, JSONL and MCP. `storage` retains tested portable serialization/checksum/fingerprint utilities and the original v1 storage helpers. Those helpers do not make v1 a readable production index in v2.

The executable does not launch subprocesses, contact services, load models, or require a language runtime. Test executables use `std::system` to exercise independent processes. Optional benchmark scripts use Python/PowerShell only as development tooling.

## Index construction

One producer enumerates the tree while a bounded byte queue feeds workers. Existing-index global scans group a bounded (up to8192 jobs / about2 MiB accounted payload) window by catalog bucket to improve locality; they still do not retain the entire file list. During strict source scans, workers hash/validate files before deciding whether capture and tokenization are needed. Explicit metadata mode can skip hashing when saved size/timestamps agree; compaction instead reads verified saved snapshot content, not current source files. Changed/new source files are captured in a segment content stream and checked against the initial fingerprint, CRC, size and timestamps. Existing unchanged documents are not tokenized again.

Each worker accumulates term frequency and earliest position for the current document, spills bounded aggregates into a multi-pass external sorter, and periodically finalizes an independent segment. The sorter merges no more than 24 runs at a time. The fast profile additionally remembers distinct 24-bit byte trigrams with a 2 MiB bitmap and a bounded touched-word list, preventing repeated occurrences from generating repeated temporary records. Compact builds can write an optional per-document literal signature for files of at least 512 source bytes. This is a bounded 128-byte mask, not an inverted trigram index; tiny or saturated documents have no entry. The additive `literal.tbl` layout and compatibility rules are specified in [FORMAT_STORAGE.md](FORMAT_STORAGE.md).

Text is scanned with fixed I/O blocks and a bounded line buffer. An invalid file is skipped with diagnostics; a file that changes after validation aborts the transaction. Filesystem enumeration errors are not interpreted as successful deletions. A repository is not an atomic snapshot of the entire filesystem: files can change after their individual stable capture. Global freshness remains unknown unless verified again.

## Metadata and generations

Stable document IDs contain a 10-bit path-hash bucket and a 54-bit monotonically allocated serial. A bucket hash is only routing: full relative UTF-8 paths are keys and collisions do not merge files. There are 1024 independent catalog B+trees. Each stores both ID→record and path→ID. An update rewrites only affected catalog buckets and writes a small new manifest. Highly skewed buckets have a budget guard, not an unbounded allocation.

A manifest references catalog generations and immutable segments with live document counts, aggregate statistics, next ID, source root and saved build policy. Updated documents point to their newest segment; older postings are filtered by the current record's segment identity. A no-op with identical policy/metadata does not publish a generation. Changing stored timestamps or policy can legitimately publish metadata without retokenizing content.

New segments are made final before catalogs and commit publication. The fully closed checked commit is renamed to `commit-G.bin` last. Before that point, readers continue opening the old commit. Failed transactions may leave unreachable temporary/orphan objects, which are harmless and reclaimed by GC. Stream flush/close and rename give a tested process-exit protocol, not an fsync-based power-loss guarantee.

## Snapshots and concurrent maintenance

Opening a snapshot takes the short `access.lock`, selects/validates a manifest and creates a checked reader pin before releasing the gate. Writers take `writer.lock`; ordinary searches do not acquire the writer lock. Each `Index` shares an immutable snapshot and can be searched concurrently. A `Service` is a sequential session, not a concurrent RPC dispatcher.

`Service` caches its `Index` across requests. A different index directory, memory setting or explicitly requested generation replaces it; an omitted generation does not automatically observe an outside writer's latest commit. Explicit refresh and the session's maintenance/write commands invalidate the cache. Cursor requests select their retained generation. Thus repeated find-only requests, update/refresh followed by find, and fresh CLI processes are distinct workloads; cache invalidation after maintenance is not an accidental per-query reopen.

GC takes both writer lock and gate, retains the requested recent commits plus every pinned generation, and computes reachable catalogs/segments. It first removes every unretained commit, then removes unreachable data. Thus a process exit during deletion cannot leave an advertised old commit whose objects were already removed. Pin removal also uses the access gate, preventing a last reader's destructor from removing the generation file while GC reads it. If the destructor cannot acquire the gate, it leaves a conservative stale pin. A crashed reader's pin is retained indefinitely until explicit offline recovery. No timer guesses whether a slow reader is dead.

Compaction reindexes current saved document content into fresh segments, retaining stable IDs and publishing a new snapshot. It does not implicitly refresh from the live workspace or delete old snapshots. GC is separate. Pins protect an independent reader across both operations, which is exercised by a subprocess test.

## Search planning

Full terms look up exact dictionary strings. Sparse terms are streamed through compressed, sorted postings; active-version filtering uses the catalog. AND adaptively chooses a selective covering anchor or intersects covering streams using monotonic seeks. A selected pure conjunction uses its cheapest live stream as the driver and checks the remaining necessary postings in each candidate's active segment, avoiding redundant catalog validation of intermediate postings. After an amortized streak of misses, a conservative next-posting lower bound across all membership segments can skip a disjoint ID range; a per-segment-only bound would not be safe. Mixed OR trees retain the generic monotone merge/intersection path. No complete posting list or candidate set is materialized, and the planner does not unconditionally intersect every list. OR unions covering anchors. NOT never subtracts approximate candidates and may require enumeration of all live documents. Path filters apply before content verification.

For phrases/regex, an AST-derived necessary condition extracts mandatory literal fragments. Optional or unknown portions weaken the condition to the universe; disjunction is a union. Fully enclosed exact tokens can supply safe posting anchors, but tokens touching a literal's edges cannot: a literal may start or end inside a longer indexed token. Fast-profile planning also samples a bounded set of byte trigrams and can intersect several covering lists according to its cost heuristic. Frequent individual trigrams are not automatically assumed to have a frequent intersection.

Compact-profile candidates may be rejected by their optional literal signature before reading content. Signatures contain every four-byte window within the same BOM/CR-normalized lines that the matcher sees, including windows inside long tokens and UTF-8 byte sequences. A missing entry, an unsupported short literal or a saturated signature provides no exclusion. Query masks contain only required bits; document-side saturation/work limits must not add requirements to a query. Boolean and regex filters propagate possible truth conservatively, including under NOT. A positive signature result is never proof of a match: the precise NFA/substr matcher still verifies candidate text. These filters can admit false positives but must not exclude actual matches. There is no general full-text speed guarantee for expressions such as `/.*/`.

Exact term truth, frequency and first position come from the index. Once a candidate record is known, other exact leaves seek only its active segment rather than merging every segment merely to test that one document. Term-only search ranks candidates without opening their content; snippets are read after selecting top-k. Regex/phrase candidates are read for exact verification, then top results may be read again to produce evidence. Regex workspaces are reused within a query.

Ranking uses term frequency, a BM25-like length normalization, inverse frequency, earlier positions, path matches and proximity of the first occurrences of positive leaves. Segment frequency is an upper estimate while obsolete versions remain; compaction can change that estimate and therefore scores. Ranking version is 2. A continuation is bound to generation, query, filters and sort so it cannot accidentally mix rankings across updates. No approximate early termination is claimed.

Dense result candidates use ordered shard decoding; sparse candidates use direct B+tree lookup and a bounded shared record LRU. Raw and decoded page LRUs are budgeted separately. Each search holds bounded dictionaries/cursors and a top-k heap. Keyset pagination keeps heap size independent of page number but still evaluates candidates for each page.

## Content reads and adaptive search workers

Each search owns a bounded content-reader cache, and each candidate worker has its own reader. Readers reuse segment `content.bin` streams and known offsets; they do not share a mutable `seekg` position across threads. The cache closes evicted streams and releases all remaining streams with its owner. A reader permits at most 32 open content streams (16 by default); worker allowances are reduced with worker count. Snapshot pins continue protecting the underlying segment lifetime. These are content-stream bounds, not a claim that the entire process opens no other files.

The scanner reads fixed-size blocks. Complete lines already in a block are consumed through views; only lines crossing a block boundary need an owning scratch buffer. UTF-8/NUL validation, first-line BOM handling, CR removal, maximum line limits and exact line counting are preserved. Fingerprint and IEEE CRC-32 are computed over the raw bytes during that same streaming pass, not by rereading the file. Saved identity checks remain enabled, including snippet reads after enough snippets have been collected.

Content-heavy candidate batches without regex can run on a bounded, lazily created worker pool. `SearchOptions::threads` is a maximum: zero selects adaptive sizing, one forces serial execution, and larger values still respect workload and memory guards. Pool startup also requires at least 2 MiB of actual enqueued content work and a sufficiently populated batch; rejected paths/signatures do not count. The byte counter is updated only after enqueue, so a large upcoming document cannot launch workers for an earlier memory-pressure flush. Small/very selective queries remain serial. Term-only queries use postings rather than a content-worker pool. Queries containing regex currently remain serial to preserve the existing query-wide NFA step budget and its deterministic charging order; setting `threads` does not change this contract.

Pending batches hold at most 128 documents per eligible worker (2048 at the 16-worker cap), with earlier pressure flushes against the logical pending-work allowance. For nonempty, reasonably balanced sizes, auxiliary indices group already-admitted documents by segment and content offset into byte-balanced worker slices. This improves locality without reordering the original pending array or increasing open-stream allowances. Empty or highly uneven batches retain striped dispatch. The auxiliary indices are included in pending-work accounting; the live-row allowance is not a strict physical cap on vector spare capacity or transient allocations.

Candidate enumeration, exact posting state and global candidate/read-budget charging remain on the calling thread. Workers fill independent document counts/first-line arrays; an ordered reduction computes exact scores, ties, totals and top-k. Successful results retain deterministic ordering and pagination rather than merging approximate per-worker rankings. Worker failures stop the batch and propagate an error, never a successful partial result. The C++ `SearchOptions::cancelled` predicate supports cooperative cancellation and must itself be thread-safe; this is not a JSONL/MCP in-flight cancellation API. Search entry and bounded intervals inside rejected/stale posting loops also poll it, so a no-match query does not need to find an evaluable candidate before observing cancellation. Every candidate-document content scan polls at entry as well as per line, including queued zero-line documents in serial and parallel flushes. Search snippet callbacks poll per line; separate public read/verify operations do not acquire a `SearchOptions` cancellation hook.

## Memory accounting and measurement

The default 256 MiB setting is an accounted workspace allowance, not an OS-enforced whole-process RSS ceiling. `Index` construction sizes shared snapshot page/record caches. Each search separately budgets result buffers, decoded documents, term sources/cursors, line workspaces, worker workspaces and pending batches from `SearchOptions::memory_mb`. Reusing an `Index` does not resize its shared caches to a later request's smaller budget. Concurrent C++ callers share snapshot caches but each add their own query allocations; admission control must account for overlapping queries. Allocator overhead, thread stacks, standard-library stream allocations and the rest of the host process require additional headroom. Sequential stdio dispatch avoids overlapping requests within one `Service`, but multiple processes/services still have independent costs.

Search stage timing is opt-in through `SearchOptions::profile`; build timing uses `BuildOptions::profile_stages`. Disabled searches do not time every input line. Search worker I/O/verification/line/matching times are accumulated across workers, while candidate and snippet phases include nested work. Build worker stages also overlap: capture includes tokenization/writing and enumeration includes producer backpressure. These counters are diagnostic, not an additive decomposition of elapsed wall time. Compare unprofiled performance separately from profiled diagnostics, and distinguish process startup, filesystem-cache state, snapshot reuse and update/refresh cycles. Exact JSON field names are documented in [AGENT_API.md](AGENT_API.md).

## What was deliberately not added

No native filesystem watcher, USN journal, mmap, platform fsync, SIMD intrinsics, content compressor, vector database, semantic embedding service or background daemon. Native APIs violate the unchanged standard-library-only requirement. Snapshot content is stored uncompressed. WAND upper-bound pruning and dense compressed bitmap postings were not necessary to implement the delivered exact streamed search and are not claimed. Performance conclusions must be supported by paired measurements, not by extrapolating a maximum document constant.
