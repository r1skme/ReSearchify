# Verified Linux file-data-cache follow-up

The accepted compact-profile run completed **126 timed searches**: three
queries, two cache modes, three executables, and seven repetitions. All **63
cold samples** had complete `mincore` observations with zero resident pages in
their inventoried file ranges before target launch. All **63 warm samples**
reported zero Linux input-block operations. Full matching-path/count checks
passed for all three queries, and final source, index, executable and driver
identity/hash checks passed.

This measures cold **file data pages in an owned disposable fixture**. It does
not measure a cold machine, cold filesystem metadata, cold executable, or cold
storage device. Both cold and warm measurements start a fresh search process.
The warm condition replays the identical query once in another fresh process;
it is not a persistent JSONL/MCP session.

## Measurement protocol

The three cases are exact term `needle_42`, literal `"needle_42 = 0;"`, and
broad regex `/needle_[0-9]+/`. Term and literal have one matching file; regex
has 100,000. ReSearchify runs complete count-only searches with 256 MiB,
`--limit 0 --snippets 0`, the default thread policy and an explicit effectively
unbounded regex-step allowance. ripgrep uses its default thread policy and
complete per-file counts. Its output cost is included; ReSearchify returns a
total rather than printing every matching path in the timed operation.
Complete path/count equivalence is checked separately outside timings.

Term/literal comparisons use ripgrep occurrence counts. Regex comparisons use
matching-line counts to match the engine contract. The 64-file smoke fixture
deliberately duplicates `needle_42` within one existing line: that document has
term count 3, literal count 1 and regex matching-line count 2. The smoke passed
18 targets, all three full-map checks, nine verified-cold observations and
nine zero-input-block warm observations. Its updated manifest describes the
actual 11,216 bytes and 512 lines. Smoke timings are not used as performance
evidence.

Preparation first called `fdatasync` on only the owned fixture's source/index
files, outside all search timings: 102,162 files, zero errors, 9.31 seconds.
Each cold attempt then applied `POSIX_FADV_DONTNEED` only to the relevant owned
files and observed every range using `mmap(PROT_NONE)` plus `mincore`. No global
`sync`, `drop_caches`, device-cache flush or unrelated file eviction occurred.
The timed target runs in a separate resource helper that never loads the large
inventory; cache preparation, observation and helper startup are excluded from
its wall/CPU time. The helper records exactly one child target's resource use.

Executables are shuffled within each repetition with seed 1729. Every
query/cache/tool distribution has the originally specified **seven samples**;
none were removed or selectively repeated. Cache modes are separate groups,
not interleaved cold/warm pairs. With seven samples, nearest-rank **p95 equals
the maximum** and should not be treated as a stable tail estimate. The raw
reports retain min/max, samples, commands, orders, observations and resource
methods. An independent read-only review recomputed every wall/CPU/RSS
distribution from the main and smoke samples and confirmed exact agreement.

The literal change retains a large improvement in both cache conditions. In
this run current ReSearchify is 5.45x faster than ripgrep on cold literal data,
but **2.29x slower on warm literal data**. Current broad regex is still **1.83x
slower than ripgrep cold and 2.58x slower warm** despite improving over the
original implementation. This evidence does not support a claim of universal
superiority over ripgrep.

Term results are a control, not evidence of a large new optimization. Warm-term
medians differ by only 0.232 ms; the median of paired original/current ratios is
1.004x. The first current cold-term sample took **59.094 ms**, so its p95/max is
worse than the original's 17.547 ms. The sample is retained; this experiment
does not establish its cause or guarantee improved term tail latency.

## Cache verification and its limits

Every cold observation checked the complete immutable data inventory:

| Tool | Inventoried files | Observed pages per cold sample | Resident pages before target | Median resident pages after term / literal / regex |
| --- | ---: | ---: | ---: | ---: |
| Original | 1,073 | 123,558 | 0 in all 21 samples | 180 / 92,631 / 92,631 |
| Current | 1,089 | 127,584 | 0 in all 21 samples | 189 / 7,777 / 96,652 |
| ripgrep source | 100,000 | 100,000 | 0 in all 21 samples | 100,000 / 100,000 / 100,000 |

`mincore` observations are sequential, not an atomic assertion about every
page at the exact instant of `exec`. The maximum pre-target observation window
was 34.1 ms for the original index, 29.9 ms for the current index and 1494.7 ms
for the 100,000 source files. The maximum delay from observation completion to
resource-worker readiness was 78.0 ms. Another process or readahead could
populate an earlier range during those gaps; the recorded scope and timestamps
make that limitation inspectable. No other benchmark target or fixture writer
ran concurrently.

Metadata is touched by setup and observation and is not evicted. Executable,
library and storage-device cache state remains uncontrolled. These measurements
are limited to native Linux x86-64, the compact profile and this generated
corpus. They do not verify Windows/macOS cold-cache behavior, fast-profile
cold-cache behavior, large-file real-project distributions, or warm-process
JSONL/MCP latency.

## Index size and separately measured preparation

The original status-reported index is **504,071,122 bytes (480.720 MiB)**;
current is **520,504,919 bytes (496.392 MiB)**, an increase of **16,433,797 bytes
or 3.26%**. This is an explicit cost of the optimized index, separate from the
search timing and RSS tradeoffs.

Each index was built once with four workers and 256 MiB during preparation:

| Preparation only, one sample | Original | Current |
| --- | ---: | ---: |
| Build wall seconds | 10.646 | 6.555 |
| Build CPU seconds | 33.798 | 25.825 |
| Peak RSS MiB | 24.352 | 24.977 |

Both builds hashed and tokenized all 100,000 files. The complete fixture
generation, hashing, index construction and scoped data cleaning took 31.37
seconds. These single preparation samples are preserved for cost accounting;
they are not a repeated indexing benchmark or a stable indexing speedup claim.

## Reproduction

The archive contains the exact one-off preparation script and its emitted
manifests. For a new location, use the same generator and build commands
recorded in the setup evidence, create a fresh disposable marker, then run:

```sh
python3 scripts/cache_benchmark.py \
  --fixture /tmp/owned-fixture/cache-fixture.json \
  --baseline /absolute/rs-original \
  --current /absolute/rs-current \
  --rg /absolute/rg \
  --iterations 7 \
  --work /tmp/new-cache-results
```

Keep source/index preparation and any scoped data cleaning outside search
timings. Preserve `advice-only` or unsupported labels if a different kernel or
filesystem cannot produce complete zero-residency observations. Do not promote
an advisory cache eviction request into a verified cold-cache result.
